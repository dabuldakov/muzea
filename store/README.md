## 3. Подпись и Play App Signing (важно для обновлений)

Новые приложения Play автоматически подписывает ключом, который генерирует
Google. Тогда APK из Google Play будет подписан **другим** ключом, чем APK с
GitHub, и пользователи, установившие APK вручную, не смогут обновиться поверх —
придётся переустанавливать.

Чтобы сохранить тот же ключ (`muzea.jks`), сделать это нужно **до** раскатки
релиза в открытое тестирование или production:

1. Создать приложение в Play Console и загрузить AAB (можно в Internal testing).
2. **Protected with Play → Play Store protection → Manage Play app signing →
   Change key**.
3. Выбрать «Provide a copy of your app signing key» и загрузить `muzea.jks`,
   зашифровав его через `pepk.jar` (инструкция в Console).
4. Upload key остаётся `muzea.jks` — им уже подписывает CI.

Если решите оставить ключ Google: приложение будет ставиться только из Play,
а для GitHub придётся скачивать universal APK из Play Console (он подписан
ключом Play) — иначе два канала несовместимы.

## 5. App content: готовые ответы

### App access (доступ для ревьюера)

Приложение требует входа. Ревьюеру нужен демо-аккаунт, а OTP приходит на почту.
Пока не сделан фиксированный код для ревью, укажите в Console:

```
Email: <демо-email>
Password/OTP: <код, который выдаётся вручную>  (см. примечание ниже)
Instructions: введите email, затем код из письма
```

**Нужно доработать:** фиксированный OTP для демо-аккаунта (например,
`review@muzea.su` → `123456`) в `muzea-auth-service`, чтобы ревьюер мог войти
без доступа к почте. Без этого приложение могут отклонить по правилу
«App access».

### Data safety

| Вопрос | Ответ |
|---|---|
| Шифрование при передаче | Да (HTTPS) |
| Удаление данных по запросу | Да — в приложении и на `https://muzea.su/delete-account` |
| Собираемые данные | Email, имя/username, фото и видео, аудио, файлы, тексты сообщений, идентификатор устройства, push-токен |
| Передача третьим лицам | Нет (Firebase Cloud Messaging — обработчик доставки push) |
| Реклама/трекинг | Нет |
| Диагностика/аналитика | Не собирается |

Разрешения в манифесте: `INTERNET`, `POST_NOTIFICATIONS`, `RECORD_AUDIO`,
`CAMERA`. Доступа к контактам, геолокации и файлам вне выбора пользователя нет.

### Content rating (IARC)

- UGC: да (чаты, новости, видео) → модерация через жалобы и блокировку.
- Обмен личными данными: да (сообщения).
- Контент 18+: нет, но есть возможность публиковать взрослый контент —
  отвечайте честно на вопросы про UGC, ожидаемая категория **Teen / 12+**.

## 6. Автоматическая загрузка в Play (по желанию)

В `.github/workflows/release.yml` уже есть шаг публикации. Чтобы он работал:

1. Google Cloud → создать сервисный аккаунт, включить **Google Play Android
   Developer API**.
2. Play Console → **Users and permissions** → пригласить сервисный аккаунт с
   правами на релизы (Admin или Release manager).
3. Скачать JSON-ключ, закодировать в base64 и положить в GitHub Secrets как
   `PLAY_SERVICE_ACCOUNT_JSON_B64`.
4. В GitHub → Variables задать `PLAY_TRACK` (`internal` для начала) и
   `PLAY_STATUS` (`completed`).

После этого каждый тег `v*` будет сам собирать AAB и загружать его в выбранный
трек.

## 7. Порядок публикации

1. Internal testing: загрузить AAB, пригласить себя и пару тестировщиков.
2. Закрытое тестирование (12+ тестеров, 14 дней) — если нужен production-доступ
   для нового личного аккаунта.
3. Production: раскатка.
