# Статусы сообщений: отправлено / доставлено / прочитано

План реализации. Решение по объёму и спорным местам — в конце документа.

## 1. Что уже есть

### Бэкенд чата (`chat-muzea`)

Подготовлена модель **watermark-ов на участника**, а не построчных статусов:

- `participants.last_delivered_message_id` / `last_delivered_at`;
- `participants.last_read_message_id` / `last_read_at`;
- индексы по обоим полям (миграция `V5__participants.sql`);
- `MessageStatusService`: `markMessagesAsRead`, `markMessageAsDelivered`,
  `getMessageStatuses`, `getMessageStatusForUser`, `isMessageReadByAll`;
- `POST /api/messages/{chatUuid}/read?upToMessageUuid=...` — отметка прочтения;
- `GET /api/messages/{chatUuid}/status/{messageUuid}` — статусы по одному
  сообщению (по участникам);
- в `MessageDto` уже есть поле `status`, но оно **не заполняется**.

Чего нет:

- **эндпоинта отметки доставки** — `markMessageAsDelivered` нигде не вызывается,
  поэтому `DELIVERED` сейчас недостижим: статус прыгает `SENT → READ`;
- **bulk-эндпоинта статусов** — текущий работает по одному сообщению (N+1);
- **имён/аватаров** в статусах — только `userId`, для «кто прочитал» этого мало;
- порядкового номера сообщения в API — клиент сравнивает watermark только по
  времени, что менее надёжно.

### Android-клиент

- Отправка и optimistic-сообщения есть (`Message`, `ChatMessageReducer`),
  статусов и «галочек» нет.
- Прочтение отправляется: `markMessagesAsRead` после каждого обновления ленты.
- Доставка не подтверждается.
- Опрос переписки — раз в 3 секунды, WebSocket/SSE нет.
- Участники чата доступны через `GET /api/chats/{chatUuid}/participants`
  (имена, аватары, роли).

Вывод: **фундамент на бэкенде готов примерно наполовину**, но сквозного сценария
(подтверждение доставки → расчёт статуса → отображение) нет. Основная работа —
контракт API и клиентская часть.

## 2. Семантика статусов

| Статус | Когда ставится | Иконка |
|--------|----------------|--------|
| `SENDING` | сообщение ещё не подтверждено сервером (локальное) | часы |
| `FAILED` | отправка не удалась | восклицательный знак, повтор |
| `SENT` | сервер принял сообщение | одна галочка |
| `DELIVERED` | устройство получателя подтвердило получение | две галочки |
| `READ` | получатель открыл чат и отметил прочтение | две синие галочки |

Правила для чатов:

- **Приватный чат** — статус считается по единственному собеседнику.
- **Группа** — галочка отражает «доставлено/прочитано **всеми** остальными
  участниками» (как в WhatsApp). При нажатии на галочку открывается список:
  кто прочитал, кто получил, кто ещё нет.
- Свои сообщения всегда считаются прочитанными автором.
- Участники, вступившие в группу **после** сообщения, не влияют на его статус.
- Сообщения, отправленные до вступления, не должны «висеть» в `SENT` из-за
  нового участника — для них его watermark не учитывается (см. `joinedAt`).

## 3. API (предлагаемый контракт)

### 3.1. Порядковый номер сообщения

Добавить в `MessageDto`:

```json
{ "messageId": 12345, "messageUuid": "...", ... }
```

`messageId` — существующий `messages.message_id` (BIGSERIAL). Внутри чата он
монотонен, по нему клиент сравнивает watermark-и без парсинга времени.

### 3.2. Подтверждение доставки

```
POST /api/messages/{chatUuid}/delivered?upToMessageUuid={uuid}
```

- авторизация как у `/read`;
- двигает `last_delivered_message_id` только вперёд;
- вызывается клиентом после получения новой порции сообщений.

### 3.3. Bulk-квитанции для галочек

```
GET /api/chats/{chatUuid}/receipts
```

```json
[
  {
    "userUuid": "...",
    "username": "anna",
    "fullName": "Anna",
    "avatarUrl": null,
    "joinedAt": "2026-10-01T10:00:00Z",
    "lastDeliveredMessageId": 12340,
    "lastDeliveredAt": "2026-11-02T18:00:00Z",
    "lastReadMessageId": 12339,
    "lastReadAt": "2026-11-02T17:59:00Z"
  }
]
```

Один запрос на чат, размер — число участников. Клиент опрашивает его вместе с
сообщениями (тот же цикл 3 с) и сам вычисляет статус каждого своего сообщения.

### 3.4. Детали «кто прочитал»

Использовать существующий `GET .../status/{messageUuid}`, но расширить
`MessageStatusDto`:

```json
{
  "userUuid": "...",
  "username": "anna",
  "fullName": "Anna",
  "avatarUrl": null,
  "status": "READ",
  "deliveredAt": "...",
  "readAt": "..."
}
```

Запрос делается **только при открытии шторки** по конкретному сообщению — не
для всей ленты.

Альтернатива: отдавать детали сразу в bulk-квитанциях (уже есть) и не трогать
per-message endpoint. Но имена в нём всё равно нужны для шторки.

## 4. Клиент: слои

### 4.1. Данные

- `MessageResponse` → `messageId: Long?`; `Message` → `sequence: Long?`.
- Новые DTO: `ChatReceiptResponse`, `MessageStatusResponse`.
- `ChatApiService`: `markMessagesAsDelivered`, `getReceipts`, `getMessageStatuses`.
- `MessageRepository`: методы + кэш квитанций по чату (in-memory, как
  `ChatMessagesCache`).

### 4.2. ViewModel

- В цикле опроса: сообщения + квитанции (параллельно или последовательно).
- После получения новых сообщений — `markDelivered(upTo = последний uuid)`.
- Расчёт статуса — отдельная чистая функция:
  `MessageStatusCalculator.status(message, receipts, myUserUuid)`,
  покрывается unit-тестами (приватный/групповой, частичное прочтение,
  участник без watermark, вступивший позже).
- Состояние: `Map<messageUuid, DeliveryStatus>` или поле в UI-модели; чтобы не
  плодить копии `Message`, статус можно держать рядом в `ChatConversationUiState`.
- Подписка на квитанции → DiffUtil обновляет только строки, у которых
  изменился статус.

### 4.3. UI

- В `item_message_outgoing.xml` рядом с `tvTime` — `tvStatus` (иконка/текст).
- Часы — пока сообщение локальное; одна галочка — `SENT`; две — `DELIVERED`;
  две синие — `READ`; «!» — `FAILED`.
- Нажатие на галочку/время открывает `MessageInfoBottomSheet`:
  - приватный чат: «Доставлено в 18:00 · Прочитано в 18:01»;
  - группа: список участников, сгруппированный по «Прочитали / Доставлено /
    Отправлено», с аватарами и временем.
- Для входящих сообщений статусы не показываются.
- Локализация: 14 языков (новые строки).

## 5. Этапы и оценка

| Этап | Работы | Оценка |
|------|--------|--------|
| 1. Контракт | `messageId`, DTO квитанций и статусов, миграций не нужно | 0.5 дня |
| 2. Бэкенд | delivered-endpoint, receipts-endpoint, имена в статусах, тесты | 1–1.5 дня |
| 3. Клиент: данные | DTO, API, репозиторий, кэш квитанций | 0.5–1 день |
| 4. Клиент: логика | расчёт статусов, подтверждение доставки, тесты | 1 день |
| 5. UI | галочки, шторка «кто прочитал», локализация, тесты | 1 день |
| 6. Проверка | два аккаунта/эмулятора, группа, офлайн, регресс | 0.5 дня |

**Итого: 4–5 рабочих дней** на полный сценарий (приватные + группы + детали).

Быстрый вариант «только галочки в приватных чатах»: **1.5–2 дня**
(delivered-endpoint + `messageId` + расчёт по одному собеседнику + галочки).
Группы и шторка «кто прочитал» добавляются вторым этапом.

## 6. Риски и крайние случаи

- **Нет WebSocket.** Статусы обновляются с задержкой до 3 секунд (цикл опроса).
  Для галочек это приемлемо; отдельный realtime — вне этого плана.
- **Несколько устройств одного пользователя.** Watermark на участника, а не на
  устройство: «доставлено» = хотя бы одно устройство. Для галочек достаточно.
- **Новые участники группы.** Учитывать `joinedAt`: сообщения до вступления не
  должны требовать их квитанций.
- **Офлайн/повторная отправка.** Локальные сообщения без `messageId` — `SENDING`;
  ошибка — `FAILED` с повтором.
- **Удалённые и отредактированные сообщения.** Статусы остаются, текст меняется;
  для hard delete строка исчезает.
- **Пагинация.** Watermark-и могут указывать на ещё не загруженное сообщение —
  сравнение по `messageId` это переживает.
- **Приватность.** Кто-то не хочет показывать «прочитано». На будущее можно
  добавить настройку «не отправлять read receipts»; в первой версии не делаем.
